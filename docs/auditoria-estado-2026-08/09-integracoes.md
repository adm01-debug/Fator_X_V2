## 0. Achado estrutural que quebra 5 integrações de uma vez

Antes da tabela: existe **um único defeito de esquema** que corta o fio de Bitrix24, OpenAI, Anthropic, Google e OpenRouter simultaneamente.

A migration `supabase/migrations/20260405225419_364c0b81-2d7d-451a-bd93-68816919ba07.sql:82` executa:

```sql
ALTER TABLE public.workspace_secrets DROP COLUMN IF EXISTS key_value;
```

O tipo gerado confirma que a coluna **não existe mais no banco vivo** (`src/integrations/supabase/types.ts:13673-13697` — só `encrypted_value bytea`).

Mas **seis** pontos de código ainda leem/escrevem `key_value`:

| Arquivo:linha                                             | Operação em `key_value`          | Consequência                                                   |
| --------------------------------------------------------- | -------------------------------- | -------------------------------------------------------------- |
| `supabase/functions/bitrix24-oauth/index.ts:73,77`        | `upsert({key_name, key_value})`  | callback OAuth falha → token nunca é gravado                   |
| `supabase/functions/bitrix24-api/index.ts:19`             | `.select('key_name, key_value')` | erro 42703 → "Bitrix24 não conectado"                          |
| `supabase/functions/crm-bitrix-sync/index.ts:62`          | `.select("key_value")`           | erro → sync nunca roda                                         |
| `supabase/functions/bitrix24-webhook/index.ts:115`        | `.eq('key_value', domain)`       | workspace nunca resolve → `no_route`                           |
| `supabase/functions/llm-gateway/index.ts:308,321,331,340` | `.select('key_value')` ×4        | BYO-key de OpenAI/Anthropic/Google/OpenRouter **sempre vazia** |
| `src/services/whatsappOutboundService.ts:70,77`           | lê `encrypted_value` como string | bytea pgp-encriptado tratado como texto → credencial ilegível  |

**Efeito líquido no llm-gateway:** a cadeia de fallback (`resolveFallbackChain`) só consegue montar 2 opções — `HF_API_TOKEN` (env) e `LOVABLE_API_KEY` (env). **Lovable AI Gateway é o único provedor LLM realmente ligado.**

## 4. Achados de segurança

Ordenados por gravidade.

### 🔴 ALTA — Segredo em texto claro no fio quebrado dos LLMs

`supabase/functions/llm-gateway/index.ts:308,321,331,340`, `bitrix24-api/index.ts:19`, `crm-bitrix-sync/index.ts:62`

O desenho pretendido lê chaves de API de terceiros como **texto claro** em `workspace_secrets.key_value`. A coluna foi removida por uma migration de hardening (`20260405225419:82`), mas o código **não foi migrado junto** — e não existe nenhuma rotina server-side de descriptografia de `encrypted_value`. Consequência dupla: (a) as integrações estão quebradas; (b) qualquer conserto ingênuo (recriar `key_value`) restauraria o armazenamento em texto claro. O conserto correto exige escrever a camada de decrypt antes.

### 🔴 ALTA — Política de RLS órfã deixa `workspace_secrets` legível por qualquer membro

`supabase/migrations/20260522143137_6f3f697f-e17d-412c-8cce-050b20b553cb.sql:62-72`

A migration que restringe a leitura de secrets a `admin/owner` executa antes:

```sql
DROP POLICY IF EXISTS "Workspace members can view secrets" ON public.workspace_secrets;
```

Mas a política permissiva original chama-se **`"Members can view workspace secrets"`** (`20260331114302_...sql:15`) — nome diferente. O `DROP IF EXISTS` é um no-op silencioso. Se a política original ainda existir no banco, as políticas de SELECT são **combinadas por OR**, e a nova restrição a admins não restringe nada: qualquer membro do workspace continua lendo a tabela de segredos. **Verificar `pg_policies` em produção antes de qualquer conserto.**

### 🟠 MÉDIA — Dois disparadores de produção apontam para um projeto Supabase estranho

- `supabase/migrations/20260722112903_e4950969-c93b-49eb-bec1-8637aa5b7e08.sql:132` → `https://fqdohnmgmtaycfwsioik.supabase.co/functions/v1/slack-alert-dispatcher`
- `supabase/migrations/20260721155600_72a5ec4e-2f3f-4e6c-920c-6ca21ac9fa07.sql:65` → `https://fqdohnmgmtaycfwsioik.supabase.co/functions/v1/whatsapp-router`
- `supabase/migrations/20260722115149_be884e60-7f6c-4a27-ae07-ddf3f70078c6.sql:4` → mesmo host

O projeto real é `qdlnzopxrlsoljcrcmzv` (`supabase/config.toml:1`, `.env.example:10`). Isso significa que **alertas de segurança** e **mensagens de WhatsApp** deste sistema estão sendo POSTados para infraestrutura de outro projeto. Se `fqdohnmgmtaycfwsioik` estiver vivo e sob controle de outra pessoa, é exfiltração de dados; se estiver morto, é apenas o motivo pelo qual nada funciona. Em ambos os casos, precisa ser corrigido antes de qualquer secret ser configurado.

### 🟠 MÉDIA — JWT anônimo de terceiro projeto hardcoded em migration

`supabase/migrations/20260722112903_e4950969-c93b-49eb-bec1-8637aa5b7e08.sql:133`

```sql
anon_key := 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ...ImZxZG9obm1nbXRheWNmd3Npb2lrIi...';
```

Chave anon é pública por natureza, então a gravidade não é "chave vazada" — é que a chave é **do projeto `fqdohnmgmtaycfwsioik`**, confirmando o vazamento de configuração acima, e está fixada em migration versionada (não rotacionável sem nova migration). Expira em 2036.

### 🟠 MÉDIA — Envio de WhatsApp direto do navegador com credenciais de provedor

`src/services/whatsappOutboundService.ts:70-77,116,183,216,258`

O código busca credenciais de Twilio/Meta/Z-API/Evolution do banco **para dentro do browser** e faz `fetch` direto para `api.twilio.com`, `graph.facebook.com`, `api.z-api.io`. Hoje não vaza nada porque a leitura está quebrada (`encrypted_value` ilegível como string) e o CORS bloqueia. Mas o desenho é o de expor tokens de provedor no cliente — se alguém "consertar" a leitura sem mover a chamada para o servidor, cria-se um vazamento real. Deve ser reescrito como edge function, não corrigido no lugar.

### 🟡 BAIXA — Guardrails de segurança falham em aberto e em silêncio

`supabase/functions/llm-gateway/index.ts:467,519,549,739,785`

Toxicidade, PII, prompt-injection, hallucination-check e classificação só executam se `HF_API_TOKEN` existir. Sem o token, cada bloco é simplesmente pulado — sem log, sem alerta, sem flag na resposta. O sistema aparenta ter guardrails ativos enquanto roda inteiramente sem eles.

### 🟡 BAIXA — `sendEmail()` mente sobre a entrega

`supabase/functions/notification-sender/index.ts:185-193`

Retorna `{ success: true }` sem enviar nada. Notificações são registradas como entregues. Um alerta crítico de compliance ou incidente ficaria marcado como "enviado" tendo desaparecido.

### 🟡 BAIXA — Fallback para project ID de terceiro no frontend

`src/pages/WidgetBuilderPage.tsx:41`

```ts
const projectId = import.meta.env.VITE_SUPABASE_PROJECT_ID || 'fqdohnmgmtaycfwsioik';
```

Mesmo padrão em `src/config/env.ts:28`, com ainda outro ID: `'tdprnylgyrogbbhgdoik'`. São **três** project IDs distintos circulando pelo repo. Fallbacks silenciosos para projetos alheios devem virar erro de inicialização.

### ✅ Não encontrado

Varredura por `sk-*`, `xoxb-*`, `hf_*`, `AIza*`, `ghp_*` em `src/`, `supabase/`, `openclaw/`, `scripts/`, `docs/`, `.github/`: **zero chaves de API reais commitadas**. O `.env.example` usa `REPLACE_ME` de forma consistente e `openclaw.json.template` usa `CHANGE_ME_*`. Higiene de segredos é boa — o problema é de arquitetura de segredos, não de vazamento.

## 5. Padrão transversal: `config.toml` tem 13 linhas para 87 edge functions

`supabase/config.toml` declara `verify_jwt = false` para exatamente **4** funções: `openclaw-webhook`, `whatsapp-router`, `rag-embed-backfill`, `slack-events-webhook`.

Todas as demais herdam `verify_jwt = true`. Isso derruba, no gateway, **toda função que precisa ser chamada por um terceiro que não emite JWT Supabase**:

| Função               | Docstring declara                       | `config.toml` | Resultado                         |
| -------------------- | --------------------------------------- | ------------- | --------------------------------- |
| `bitrix24-webhook`   | `verify_jwt: false` (linha 33)          | ausente       | Bitrix24 → 401                    |
| `whatsapp-webhook`   | `verify_jwt: false` (linha 12)          | ausente       | Twilio/Meta/Z-API/Evolution → 401 |
| `a2a-server`         | endpoint público de descoberta          | ausente       | agentes externos → 401            |
| `datahub-mcp-server` | "acessível por Claude Desktop, VS Code" | ausente       | clientes MCP → 401                |
| `webhook-receiver`   | receptor genérico com HMAC              | ausente       | qualquer emissor → 401            |

**Este é o defeito de maior alavancagem do lote:** cinco integrações têm verificação de assinatura implementada corretamente (HMAC constant-time, janela de replay, dedupe) e ainda assim nenhuma requisição chega a executá-la, porque o gateway rejeita antes. São 5 linhas de configuração.
